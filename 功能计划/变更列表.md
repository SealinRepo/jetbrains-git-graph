# JetBrains IDEA 变更列表管理功能 — VS Code 插件需求文档

## 1. 背景与目标

### 1.1 项目背景

JetBrains IDEA 的“变更列表”（Changelists）功能允许开发者将未提交的本地更改按逻辑任务分组，每个变更列表可独立提交，而不影响其他分组中的更改。VS Code 原生 Git 集成不具备此能力：所有修改默认进入统一的“更改”区域，无法在提交前进行任务级别的组织。

### 1.2 项目目标

在 VS Code 中开发一个插件，**1:1 复刻 IDEA 变更列表管理的核心交互与行为**，使用户能够在 VS Code 的源代码管理视图中创建、切换、管理多个变更列表，并将工作区更改按需分组、独立提交。

### 1.3 目标用户

- 从 JetBrains IDE 迁移到 VS Code 的开发者
- 在单一工作区并行处理多个任务、希望分离提交的开发者
- 需要在不提交全部更改的情况下，选择性提交部分工作的开发者


## 2. 术语定义

| 术语 | 定义 |
|---|---|
| **变更列表（Changelist）** | 一组逻辑关联的未提交文件更改的集合。在 IDEA 中显示为提交工具窗口中的一个分组。 |
| **活动变更列表（Active Changelist）** | 当前“接收”新更改的变更列表。所有新的文件修改自动归入活动变更列表。 |
| **默认变更列表（Default Changelist）** | 初始存在的唯一变更列表，通常命名为“Changes”或“默认”。不可删除。 |
| **非活动变更列表（Inactive Changelist）** | 用户创建但不处于活动状态的变更列表。其文件更改仍保留在工作区中，但不自动接收新更改。 |
| **变更列表冲突（Changelist Conflict）** | 用户尝试编辑一个属于非活动变更列表的文件时，IDEA 触发的冲突解决场景。 |
| **工作区（Working Tree）** | 文件系统中未提交的实际文件状态。变更列表仅记录分组关系，不改变文件内容。 |


## 3. 功能需求

### 3.1 核心数据模型

#### 3.1.1 变更列表

| 属性 | 类型 | 说明 |
|---|---|---|
| `id` | string | 唯一标识符（UUID），持久化存储 |
| `name` | string | 用户指定的名称，显示在 UI 中 |
| `comment` | string（可选） | 创建时填写的注释，提交时可预填到提交消息框 |
| `isActive` | boolean | 当前是否为活动变更列表 |
| `isDefault` | boolean | 是否为默认变更列表（不可删除） |
| `color` | string（可选） | 用于差异装饰和文件标识的颜色值 |
| `createdAt` | timestamp | 创建时间，用于排序 |

#### 3.1.2 文件归属

| 属性 | 类型 | 说明 |
|---|---|---|
| `fileUri` | string | 文件在仓库中的相对路径 |
| `changelistId` | string | 所属变更列表的 ID |
| `repoRoot` | string | 所属仓库根路径（支持多根工作区） |

**约束**：
- 一个文件只能归属于一个变更列表（MVP 版本按文件级别管理，不支持同一文件跨多个变更列表）。
- 新创建或首次检测到更改的文件，自动归入当前活动变更列表。

### 3.2 视图与 UI

#### 3.2.1 源代码管理视图集成

在 VS Code 源代码管理面板中，创建一个专用的视图容器：

- **视图名称**：Changelists（或“变更列表”）
- **位置**：源代码管理侧边栏，与 Git 视图并列（参考 `scm/title` 菜单位置）
- **视图结构**：

```
Changelists
├── 📁 [活动变更列表名称] （活动状态标记）
│   ├── 📄 modified_file1.ts
│   ├── 📄 deleted_file2.js
│   └── 📄 new_file3.ts
├── 📁 [其他变更列表1]
│   ├── 📄 modified_file4.ts
│   └── 📄 modified_file5.ts
├── 📁 [其他变更列表2]
│   └── 📄 modified_file6.ts
└── 📁 未版本控制文件 （如果有未跟踪的文件）
    └── 📄 untracked_file.ts
```

#### 3.2.2 变更列表节点

| 功能 | 交互方式 | 说明 |
|---|---|---|
| **创建变更列表** | 视图标题栏 `+` 按钮 / 命令面板 | 弹出输入框，要求输入名称（可选输入注释） |
| **设为活动** | 右键菜单 / 单击节点（可配置） | 将选中变更列表设为活动，新更改自动归入 |
| **重命名** | 右键菜单 | 仅修改显示名称，不影响文件归属 |
| **删除** | 右键菜单 | 删除变更列表，其文件移至默认变更列表（需确认） |
| **提交变更列表** | 右键菜单 / 内联按钮 | 提交该变更列表中的所有文件，不影响其他列表 |
| **显示差异** | 右键菜单 | 打开该变更列表所有文件的变更对比视图 |

#### 3.2.3 文件节点

| 功能 | 交互方式 | 说明 |
|---|---|---|
| **查看变更** | 单击文件 | 打开当前文件与 HEAD 的差异对比 |
| **移动到变更列表** | 右键菜单 / 拖拽 | 将文件移至目标变更列表（可选择现有或新建） |
| **从变更列表移除** | 右键菜单 | 将文件移回默认变更列表 |
| **提交单个文件** | 右键菜单 | 提交该文件（需确认） |

#### 3.2.4 拖拽支持

- 支持将文件从一个变更列表拖拽到另一个变更列表。
- 支持多选文件后拖拽。
- 拖拽至“新建变更列表”区域时触发创建流程。

### 3.3 活动变更列表管理

#### 3.3.1 活动变更列表的行为

- 初始状态下，默认变更列表为活动变更列表。
- 用户编辑文件产生新更改时，如果该文件已属于某变更列表（非活动），新更改**不会**自动归属到活动变更列表；文件保持其原有归属。
- 用户编辑一个**之前无更改的文件**（如新增修改），该文件自动归入当前活动变更列表。

#### 3.3.2 切换活动变更列表

- 用户可通过右键菜单“Set as Active Changelist”或单击（取决于配置）将任意变更列表设为活动。
- 切换后，之前活动变更列表中的文件保留在原列表；新的更改归入新活动列表。
- 状态栏可显示当前活动变更列表名称（可选功能）。

### 3.4 变更列表冲突处理

当用户尝试编辑一个属于**非活动变更列表**的文件时，IDEA 默认弹出冲突解决对话框。本插件的对应实现：

#### 3.4.1 冲突检测

- 监听 `workspace.onDidChangeTextDocument` 或文件保存事件。
- 判断被修改的文件是否属于非活动变更列表。
- 如果是，且用户启用了冲突检测，则触发冲突处理流程。

#### 3.4.2 冲突解决选项（可配置）

在设置中提供以下行为选项：

| 选项 | 说明 |
|---|---|
| **将更改移至活动变更列表** | 文件整体移至当前活动列表 |
| **切换到该变更列表** | 将该文件所属列表设为活动，后续更改归入 |
| **暂存更改（Shelve）** | 当前不实现，标记为未来功能 |
| **忽略** | 不处理，文件继续在其原列表中累积更改 |

#### 3.4.3 可视化提示

- 属于非活动变更列表的文件，在编辑器标签页和资源管理器中显示为**浅蓝色**（可配置）。
- 如果文件有未解决的冲突，显示**黄色条纹**或**红色字体**标记。

### 3.5 提交行为

#### 3.5.1 提交单个变更列表

- 用户右键某变更列表 → “Commit Changelist”。
- 插件执行以下 Git 操作：
  1. 将**不属于**该变更列表的其他更改从暂存区中移除（或使用 `git stash` 策略隔离）
  2. 仅暂存该变更列表中的文件
  3. 打开 VS Code 提交输入框，预填变更列表的注释（如有）
  4. 用户确认后执行提交
  5. 提交完成后，该变更列表中的文件从列表移除（文件已提交）
  6. 其他变更列表的更改保持不变，仍在工作区中

**关键约束**：提交一个变更列表不得影响其他变更列表中未提交的更改。推荐实现方式为：使用 `git apply --cached` 或精细化的暂存区操作，**不修改工作区文件内容**。

#### 3.5.2 提交多个文件（选择性提交）

- 用户在多选文件后，右键 → “Commit Selected Files”。
- 流程与提交变更列表类似，但提交范围限定于选中的文件。

#### 3.5.3 提交默认变更列表

- 默认变更列表的提交行为与其他列表一致，但“删除”操作被禁用。

### 3.6 设置项

| 设置键 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `changelists.autoCreateOnExternalActions` | boolean | false | 在执行 Cherry-pick、Revert 等操作时自动创建变更列表 |
| `changelists.allowSameFileInMultiple` | boolean | false | 是否允许同一文件出现在多个变更列表中（MVP 暂不支持，设为只读或隐藏） |
| `changelists.highlightInactiveFiles` | boolean | true | 用浅蓝色高亮非活动变更列表中的文件 |
| `changelists.conflictBehavior` | enum | `prompt` | 冲突处理方式：`prompt`（弹出对话框）、`move`（自动移入活动列表）、`switch`（自动切换活动列表）、`ignore`（忽略） |
| `changelists.removeEmptyChangelists` | enum | `silent` | 空变更列表变为非活动时的处理：`doNothing`、`silent`（静默删除）、`confirm` |
| `changelists.showEmptyChangelists` | boolean | true | 是否在视图中显示无文件的变更列表 |
| `changelists.storageFile` | string | `.git/changelists.json` | 变更列表归属关系的持久化文件路径（相对于仓库根） |


## 4. 非功能需求

### 4.1 性能

- 视图刷新应在 300ms 内完成（对于典型项目规模 < 1000 个变更文件）。
- 文件变更检测应采用事件驱动（`workspace.onDidChangeTextDocument`、`workspace.onDidSaveTextDocument`）+ 节流，避免频繁全量扫描。
- Git 操作（暂存、提交）应在后台执行，不阻塞 UI。

### 4.2 持久化

- 变更列表的归属关系存储在仓库的 `.git/changelists.json` 中，**不纳入版本控制**（`.git` 目录天然不被 Git 追踪）。
- 存储格式示例：

```json
{
  "version": 1,
  "changelists": [
    {
      "id": "uuid-1",
      "name": "Feature: Auth",
      "comment": "OAuth2 implementation",
      "isDefault": false,
      "createdAt": 1730000000000
    }
  ],
  "assignments": {
    "src/auth.ts": "uuid-1",
    "src/config.ts": "uuid-1"
  },
  "activeChangelistId": "uuid-1"
}
```

- 变更列表状态与工作区一一对应；多根工作区中每个仓库独立管理。

### 4.3 兼容性

- VS Code 最低版本：**1.85.0**（基于当前稳定 API）。
- 依赖 Git 扩展 API（`vscode.git`）获取仓库状态和文件更改列表。
- 支持 Git 仓库的基本状态：修改、新增、删除、重命名、冲突。

### 4.4 安全性

- 提交操作需用户明确确认（可通过设置关闭）。
- 删除变更列表时，文件移回默认列表而非丢弃更改。
- 任何 Git 操作不得导致用户工作区文件内容丢失。


## 5. 技术实现建议

### 5.1 VS Code SCM API 使用

- 使用 `vscode.scm.createSourceControl()` 创建独立的 SCM 实例，或复用现有 Git 仓库的 SCM 实例并通过 `createResourceGroup` 创建变更列表分组。
- **推荐方案**：创建独立的 SourceControl 实例，避免与 Git 扩展的默认视图冲突。
- 使用 `SourceControlResourceState` 表示文件节点，通过 `group` 属性关联到所属变更列表的 `SourceControlResourceGroup`。
- 使用 `scm/resourceState/context` 和 `scm/resourceGroup/context` 菜单贡献点注册右键菜单命令。

### 5.2 与 Git 扩展的协作

- 通过 `vscode.extensions.getExtension('vscode.git')` 获取 Git API，读取仓库状态（`Repository.state.workingTreeChanges`）。
- 监听 Git 仓库的状态变化事件（`Repository.state.onDidChange`），触发变更列表视图刷新。
- 对于提交操作，调用 Git API 的 `Repository.commit()` 方法，或直接执行 `git` 命令。

### 5.3 文件归属的检测逻辑

- **已有归属的文件**：当 Git 报告文件有新更改时，检查该文件是否已在 `assignments` 中。如果在，保留其原有归属。
- **新文件或此前无更改的文件**：如果文件不在 `assignments` 中（或此前无更改），归入当前活动变更列表。
- **文件更改被撤销后重新出现**：视为“新更改”，归入活动变更列表。

### 5.4 提交的隔离策略

提交单个变更列表时，核心挑战是**仅将该列表的文件纳入提交**。推荐流程：

1. 保存当前 Git 索引状态（可选）
2. 执行 `git reset HEAD .`（清空暂存区，不影响工作区）
3. 执行 `git add <file1> <file2> ...`（仅暂存目标变更列表中的文件）
4. 执行 `git commit -m "<message>"`
5. 其他变更列表的文件保持在工作区中，未被暂存或提交

此策略假设用户不手动使用 Git 暂存区（`git add`）。如果用户手动暂存了某些文件，插件应在提交前提示或自动处理。


## 6. 验收标准

### 6.1 核心场景

| 编号 | 场景 | 预期行为 |
|---|---|---|
| AC-1 | 创建变更列表 | 视图中出现新节点，默认为非活动 |
| AC-2 | 设为活动 | 新更改归入该列表，状态栏更新 |
| AC-3 | 移动文件 | 文件从原列表消失，出现在目标列表 |
| AC-4 | 提交单个变更列表 | 仅该列表文件被提交，其他更改保留 |
| AC-5 | 删除变更列表 | 列表消失，文件出现在默认列表中 |
| AC-6 | 编辑非活动列表文件 | 根据 `conflictBehavior` 设置，触发对应行为 |
| AC-7 | 重启 VS Code | 变更列表归属关系保持不变 |

### 6.2 边界条件

- 空变更列表：允许存在，提交时空列表不可提交。
- 默认变更列表：不可删除、不可重命名（IDEA 行为如此）。
- 仓库切换：变更列表状态随仓库切换而变化。
- 多根工作区：每个仓库独立管理变更列表。


## 7. 排除范围（MVP 不实现）

以下 IDEA 高级功能明确不在本期范围内：

- **Shelve/Unshelve**（搁置）功能
- **将单个文件内的不同代码块拆分到不同变更列表**（hunk-level 粒度）
- **本地历史记录（Local History）集成**
- **Cherry-pick / Revert 时的自动变更列表创建**
- **任务上下文切换（Task Context）集成**
- **多变更列表的拖拽排序**
