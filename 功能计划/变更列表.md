# IntelliJ IDEA 变更列表管理功能 — VS Code 插件完整需求文档

**文档版本**：v2.0（按操作顺序重构）
**参考基准**：JetBrains IDEA 变更列表功能
**目标环境**：VS Code Extension API 1.85.0+
**核心目标**：在 VS Code 源代码管理视图中 1:1 复刻 IDEA 变更列表管理功能


## 1. 功能概述

预期效果：文件A修改第10行文本，进入默认变更列表，然后将文件A从默认列表移入自定义列表1，此时只有自定义列表1显示文件A，默认列表不再显示；接着修改文件A第20行文本，此时第20行的变更应该进入默认列表，提交默认列表时，只提交文件A第20行的修改内容，提交默认列表后自定义列表1中第10行的修改依旧未被提交；接着可以再修改文件A第30行文本，文件A再次出现在默认列表中，将默认列表中的文件A移入自定义列表1，此时自定义列表1中的文件A应该累加移入的修改行，即未提交的行变为之前的第10行和本次移入的第30行。总的来说，处于版本控制中的文件修改后，如果该行没有所属变更列表时，则该行的修改进入默认列表，将文件从一个列表移入其他列表后，将源列表中这个文件的所有修改行累加到目标列表，从设计上来说，文件的同一个行号不会出现在多个变更列表中。

变更列表是 Git 仓库中尚未提交的本地更改的集合，用于将不同任务相关的文件更改分组，以便独立提交。本插件在 VS Code 源代码管理面板中实现 IDEA 风格的变更列表管理，支持：

- 多变更列表的创建、重命名、删除、激活
- 文件在变更列表之间的移动（右键菜单 + 拖拽）
- **同一文件的不同修改行放入不同变更列表**
- 提交时只提交选中列表的文件
- 变更列表冲突检测与处理


## 2. 视图结构与菜单布局（操作顺序起点）

### 2.1 源代码管理视图总体结构

插件在 VS Code 源代码管理侧边栏中创建以下视图层级：

```
源代码管理（SCM 面板）
├── [现有 Git 视图]（保持不变）
└── 变更列表（Changelists）视图 ← 本插件新增
    ├── 变更列表 A（活动）
    │   ├── file1.ts
    │   └── file2.js
    ├── 变更列表 B
    │   └── file3.ts
    └── 未版本控制文件
        └── new_file.ts
```

**视图标题栏按钮**：
- `+` 创建变更列表
- `⟳` 刷新
- `⋯` 更多操作

### 2.2 右键菜单层级设计

这是操作顺序中**最先需要处理**的部分。当前插件右键菜单仅有**剪切、复制、粘贴**三个选项，需要重新规划菜单层级。

#### 2.2.1 第一级菜单：[文件] 菜单

将现有的剪切、复制、粘贴操作统一归入 **`[文件]`** 一级右键菜单下：

```
右键点击文件节点
└── [文件]  ← 新增一级子菜单（可展开）
    ├── 剪切
    ├── 复制
    └── 粘贴
```

**VS Code 菜单贡献配置示例**（`package.json`）：

```json
{
  "menus": {
    "scm/resourceState/context": [
      {
        "submenu": "changelist.file.operations",
        "group": "1_file@1"
      }
    ]
  },
  "submenus": [
    {
      "id": "changelist.file.operations",
      "label": "[文件]"
    }
  ]
}
```

#### 2.2.2 第二级菜单：变更列表操作

在 `[文件]` 菜单之后，新增 **`[变更列表]`** 一级右键菜单（仅在文件节点上显示移动相关操作，在变更列表节点上显示列表管理操作）。

### 2.3 上下文差异化菜单

**关键规则**：在**文件节点**上右键与在**变更列表节点**上右键时，显示的功能菜单必须不同。

#### 文件节点右键菜单：

```
[文件]
  ├── 剪切
  ├── 复制
  └── 粘贴
──────────────
[变更列表]
  ├── 移入其他变更列表...    ← 文件专属
  ├── 新建变更列表并移入...   ← 文件专属
  └── 从变更列表移除          ← 文件专属
──────────────
提交选中文件                ← 文件专属
```

#### 变更列表节点右键菜单：

```
[变更列表]
  ├── 重命名                  ← 列表专属
  ├── 删除变更列表            ← 列表专属
  ├── 设置为活动变更列表       ← 列表专属
  └── 新建变更列表...          ← 列表专属
──────────────
提交此变更列表              ← 列表专属
显示差异                    ← 列表专属
```

**VS Code 菜单贡献配置**：

```json
{
  "menus": {
    "scm/resourceState/context": [
      { "command": "changelist.moveTo", "when": "scmProvider == changelists", "group": "2_changelist@1" },
      { "command": "changelist.commitSelectedFiles", "when": "scmProvider == changelists", "group": "3_commit@1" }
    ],
    "scm/resourceGroup/context": [
      { "command": "changelist.rename", "when": "scmProvider == changelists", "group": "1_list@1" },
      { "command": "changelist.delete", "when": "scmProvider == changelists", "group": "1_list@2" },
      { "command": "changelist.setActive", "when": "scmProvider == changelists", "group": "1_list@3" },
      { "command": "changelist.commit", "when": "scmProvider == changelists", "group": "2_commit@1" }
    ]
  }
}
```

> **说明**：`scm/resourceState/context` 用于文件节点的右键菜单，`scm/resourceGroup/context` 用于变更列表节点的右键菜单。


## 3. 核心数据模型

### 3.1 变更列表结构

| 属性 | 类型 | 说明 |
|---|---|---|
| `id` | string | UUID 唯一标识 |
| `name` | string | 显示名称 |
| `comment` | string | 可选注释（提交时预填到消息框） |
| `isActive` | boolean | 是否为活动变更列表 |
| `isDefault` | boolean | 是否为默认列表（不可删除） |
| `createdAt` | timestamp | 创建时间 |

### 3.2 文件变更归属结构

**注意**：为支持“同一文件的不同修改行放入不同变更列表”，文件归属需支持**行级（Hunk 级）**粒度。

```json
{
  "assignments": {
    "src/auth.ts": {
      "changelistId": "uuid-1",
      "hunks": [
        { "startLine": 10, "endLine": 25, "changelistId": "uuid-1" },
        { "startLine": 40, "endLine": 55, "changelistId": "uuid-2" }
      ]
    }
  }
}
```

**简化模型**（MVP 可选）：文件整体归属一个列表，行级分配通过提交时的临时勾选实现。


## 4. 操作流程（按用户操作顺序）

### 4.1 创建变更列表

**操作步骤**：
1. 用户在变更列表视图标题栏点击 `+`，或右键空白区域选择“新建变更列表”
2. 弹出输入框（QuickPick 或 InputBox），要求输入：
   - 名称（必填）
   - 注释（可选）
3. 确认后，新变更列表出现在视图中，默认为**非活动状态**
4. 如果当前没有活动变更列表，新列表自动设为活动

**IDEA 行为参考**：在 Changes 视图中右键文件 → New Changelist，指定名称和描述。

### 4.2 设置为活动变更列表

**操作步骤**：
1. 用户右键点击目标变更列表节点
2. 选择“设置为活动变更列表”
3. 该列表的 `isActive` 设为 `true`，原活动列表的 `isActive` 设为 `false`
4. 此后所有**新的文件更改**自动归入该列表

**行为规则**：
- 初始状态下，默认变更列表为活动状态
- 用户编辑一个**此前无更改的文件**时，该文件自动归入活动列表
- 用户编辑一个**已属于某变更列表的文件**时，新更改归入该文件原有的变更列表（而非活动列表）

### 4.3 在变更列表之间移动文件

#### 4.3.1 通过右键菜单移动

**操作步骤**：
1. 用户右键点击文件节点
2. 选择 `[变更列表]` → `移入其他变更列表...`
3. 弹出选择框，显示所有现有变更列表，并提供“新建变更列表”选项
4. 选择目标列表后：
   - 文件从当前列表移除
   - 文件加入目标列表
   - 文件的工作区内容**不变**

**IDEA 行为参考**：选择文件 → 右键 → Move to Another Changelist，在对话框中选择现有列表或输入新列表名称。

#### 4.3.2 通过拖拽移动

**操作步骤**：
1. 用户在视图中选中一个或多个文件
2. 按住鼠标拖动到目标变更列表节点上
3. 释放鼠标：
   - 文件从原列表移至目标列表
   - 目标列表高亮显示拖放反馈
4. 拖拽到“新建变更列表”区域时，触发创建流程

**IDEA 行为参考**：变更列表之间支持文件拖拽。

### 4.4 重命名变更列表

**操作步骤**：
1. 右键变更列表节点 → “重命名”
2. 弹出输入框，预填当前名称
3. 确认后，仅修改显示名称，**不影响**文件归属

### 4.5 删除变更列表

**操作步骤**：
1. 右键变更列表节点 → “删除变更列表”
2. 弹出确认对话框：“删除后，该列表中的文件将移入默认变更列表”
3. 确认后：
   - 变更列表被删除
   - 其中的所有文件归属改为默认变更列表
   - 文件的工作区内容不变

**约束**：默认变更列表不可删除，菜单项应置灰或隐藏。

### 4.6 变更列表冲突处理

**触发场景**：用户尝试编辑一个属于**非活动变更列表**的文件。

**检测机制**：
- 监听 `workspace.onDidChangeTextDocument`
- 判断被修改文件是否属于非活动变更列表

**冲突解决选项**（在设置中可配置）：

| 选项 | 行为 |
|---|---|
| **提示**（默认） | 弹出对话框让用户选择处理方式 |
| **移至活动列表** | 文件整体移至当前活动变更列表 |
| **切换到该列表** | 将该文件所属列表设为活动 |
| **忽略** | 不做任何处理，文件继续累积更改 |

**可视化提示**：
- 属于非活动变更列表的文件，在编辑器标签和资源管理器中显示为**浅蓝色**
- 有未解决冲突的文件，显示**黄色条纹**或**红色字体**


## 5. 行级（Hunk 级）变更列表 —— 重点功能

### 5.1 功能定位

IDEA 支持将**同一文件内的不同修改行**分配到不同的变更列表。设置项为：“Allow putting changes within one file into different changelists”。

### 5.2 数据结构设计

每个文件的 `assignments` 条目包含一个 `hunks` 数组，记录行范围到变更列表的映射：

```json
{
  "src/service.ts": {
    "hunks": [
      {
        "changelistId": "feature-A",
        "startLine": 15,
        "endLine": 32,
        "contentHash": "a1b2c3..."
      },
      {
        "changelistId": "bugfix-B",
        "startLine": 58,
        "endLine": 71,
        "contentHash": "d4e5f6..."
      }
    ]
  }
}
```

**关键字段说明**：
- `contentHash`：记录该 hunk 内容的哈希值，用于检测文件变更后 hunk 是否仍然有效
- 当文件被修改时，重新计算 hunk 范围；如果无法匹配原有 hunk，将其归入活动变更列表

### 5.3 用户操作流程

**将部分修改行归入不同变更列表**：

1. 用户在编辑器中修改文件的多处代码
2. 打开变更列表视图，文件出现在活动变更列表下
3. 右键该文件 → `[变更列表]` → `按行分配变更列表...`
4. 弹出视图显示该文件的所有 diff hunk（类似 `git add -p` 的界面）
5. 用户为每个 hunk 选择目标变更列表
6. 确认后：
   - 文件的各个 hunk 按分配归属到不同列表
   - 文件在视图中可能**同时出现在多个变更列表中**

### 5.4 提交时的行级隔离

**提交单个变更列表时，只暂存该列表中已分配的 hunk**：

```bash
# 对每个文件，提取分配给目标列表的 hunk
git diff HEAD -- <file> | filter-hunks --changelist=<target> | git apply --cached
# 然后提交
git commit -m "<message>"
```

**VS Code 现有能力参考**：VS Code 已支持“Stage Selected Ranges”命令，可选择编辑器中的行范围进行暂存。本插件在此基础上增加**变更列表归属**的维度。


## 6. 提交功能

### 6.1 提交单个变更列表

**操作步骤**：
1. 右键变更列表节点 → “提交此变更列表”
2. 系统执行隔离暂存：
   - 对于整文件归属：`git add <file1> <file2>`
   - 对于行级归属：使用 `git apply --cached` 仅暂存指定 hunk
3. 打开 VS Code 提交输入框，预填变更列表的注释
4. 用户确认提交
5. 提交后：
   - 已提交的文件/行从变更列表移除
   - **其他变更列表的更改保持不变**

### 6.2 提交选中文件

**操作步骤**：
1. 用户在文件节点上多选（Ctrl/Cmd + 点击）
2. 右键 → “提交选中文件”
3. 仅暂存并提交选中的文件（或其已分配的 hunk）
4. 其他文件保持不变

### 6.3 提交隔离的核心约束

**提交一个变更列表不得影响其他列表中的未提交更改**。

推荐实现流程：
1. 保存当前索引状态
2. `git reset HEAD .` 清空暂存区（不影响工作区）
3. 按目标列表的归属，暂存对应文件或 hunk
4. `git commit`
5. 其他列表的文件保持在**未暂存**状态


## 7. 设置项

| 设置键 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `changelists.allowMultiChangelistPerFile` | boolean | `false` | 允许同一文件的不同行放入不同变更列表 |
| `changelists.highlightInactiveFiles` | boolean | `true` | 用浅蓝色高亮非活动列表中的文件 |
| `changelists.conflictBehavior` | enum | `prompt` | 冲突处理：`prompt`/`move`/`switch`/`ignore` |
| `changelists.removeEmptyChangelists` | enum | `silent` | 空列表变为非活动时：`doNothing`/`silent`/`confirm` |
| `changelists.showEmptyChangelists` | boolean | `true` | 是否显示无文件的变更列表 |
| `changelists.storageFile` | string | `.git/changelists.json` | 持久化文件路径 |


## 8. 持久化

变更列表归属关系存储在仓库的 `.git/changelists.json` 中，**不纳入版本控制**。

```json
{
  "version": 2,
  "changelists": [
    { "id": "uuid-1", "name": "Feature: Auth", "isDefault": false, "createdAt": 1730000000000 }
  ],
  "assignments": {
    "src/auth.ts": {
      "hunks": [
        { "changelistId": "uuid-1", "startLine": 10, "endLine": 25 }
      ]
    }
  },
  "activeChangelistId": "uuid-1"
}
```


## 9. 技术实现要点

### 9.1 VS Code SCM API 使用

- 使用 `vscode.scm.createSourceControl()` 创建独立 SCM 实例
- 使用 `createResourceGroup()` 创建变更列表分组
- 使用 `SourceControlResourceState` 表示文件节点
- 菜单贡献点：`scm/resourceState/context`（文件）、`scm/resourceGroup/context`（列表）

### 9.2 行级暂存实现

- 调用 `git diff HEAD -- <file>` 获取完整 patch
- 按 hunk 边界拆分 patch
- 根据 `assignments.hunks` 筛选目标 hunk
- 用 `git apply --cached` 仅暂存选中 hunk

### 9.3 拖拽支持

- VS Code TreeView 原生支持拖拽（`TreeDragAndDropController`）
- 或者自定义 webview 实现更灵活的拖拽交互

| 编号 | 场景 | 预期行为 |
|---|---|---|
| AC-1 | 右键文件节点 | 显示 `[文件]` 和 `[变更列表]` 菜单，菜单项与列表节点不同 |
| AC-2 | 右键列表节点 | 显示重命名、删除、设为活动等列表专属菜单 |
| AC-3 | 创建变更列表 | 出现在视图中，非活动状态 |
| AC-4 | 设为活动 | 新更改归入该列表 |
| AC-5 | 右键移动文件 | 文件从原列表移至目标列表 |
| AC-6 | 拖拽文件 | 拖到目标列表后归属改变 |
| AC-7 | 行级分配 | 同一文件的不同 hunk 出现在不同列表中 |
| AC-8 | 提交单个列表 | 仅该列表的文件/hunk 被提交 |
| AC-9 | 删除列表 | 文件移回默认列表，工作区不变 |
| AC-10 | 重启 VS Code | 归属关系保持不变 |
