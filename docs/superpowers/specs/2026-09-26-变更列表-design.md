# 变更列表（Changelists）功能 — 设计文档

**日期**：2026-09-26
**状态**：草案，待用户审阅
**关联需求**：`功能计划/变更列表.md`（v2.0）
**参考实现**：JetBrains IDEA 的 Changes 视图

---

## 一、目标与边界

在 VS Code 中实现 IDEA 风格的「变更列表」管理：把 working tree 中尚未提交的更改按任务/特性分组到多个列表里，提交时可只提交某一个列表的内容。完整支持文档 v2.0，包括同一文件的不同行归属到不同列表（hunk-level）。

集成到现有 `git-brains.commitPanel`（Commit webview）中作为新 tab，不另开面板、不注册 VS Code 原生 SCM provider。所有变更列表状态通过单一 `MessageRouter` 与现有 `worktreeChanged` / `stashChanged` 事件管线共存。

### 用户已确认的范围决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 范围 | 完整版（含行级 hunk） | 用户选择 |
| UI 位置 | Commit webview 内新增 "Changelists" tab | 用户选择，避免与内置 Git SCM 重复渲染 |
| 行号跟踪策略 | 固定行号（简单） | 文件改动后失配的 hunk 自动回退到整文件归属 |
| 默认变更列表 | 显式 "Changes" 默认列表，永不可删 | 贴合 IDEA 习惯 |
| 编辑冲突行为 | 通过设置 `changelists.conflictBehavior` 配置（默认 `prompt`） | 灵活、可零配置运行 |
| 持久化位置 | `<workspaceRoot>/.vscode/jetgit-changelists.json` | 用户选择，避免污染 `.git/` |
| 设置键 | 完整 6 个键 + `commitMessagePrefill` | 与文档 §7 一致 |
| 架构模式 | Service + Router（A 方案） | 与项目现有架构一致，无乐观更新 |

## 二、数据模型

### 2.1 持久化文件

路径：`<workspaceRoot>/.vscode/jetgit-changelists.json`

版本号 `version: 2` 表示支持 hunk-level 分配；旧版本 v1（仅整文件）数据加载时自动迁移。

```ts
interface ChangelistsFile {
  version: 2;
  changelists: Changelist[];
  /** 当前活动变更列表 id；新未分配文件进入此列表 */
  activeChangelistId: string;
  /** 默认 "Changes" 列表 id，永不改变 */
  defaultChangelistId: string;
  /** key = 仓库相对路径（POSIX 分隔符），value = 文件分配 */
  assignments: Record<string, FileAssignment>;
}

interface Changelist {
  id: string;             // uuid v4
  name: string;           // 唯一，校验：非空、与现有名不重复（大小写不敏感）
  comment: string;        // 提交时预填到 message 输入框
  isDefault: boolean;     // 仅 "Changes" 为 true
  createdAt: number;      // epoch ms
}

interface FileAssignment {
  /** 整文件所属列表。设置后 hunks 字段被忽略（除非显式清空） */
  changelistId: string;
  /** 可选：行级分配。存在时文件在多个列表中同时显示 */
  hunks?: HunkAssignment[];
}

interface HunkAssignment {
  /** 工作区行号，1-indexed，inclusive。固定行号策略 */
  startLine: number;
  /** 1-indexed，inclusive */
  endLine: number;
  changelistId: string;
}
```

### 2.2 首次运行默认值

JSON 文件不存在时，在内存中创建：

```json
{
  "version": 2,
  "changelists": [
    { "id": "default", "name": "Changes", "isDefault": true, "comment": "", "createdAt": 1737000000000 }
  ],
  "activeChangelistId": "default",
  "defaultChangelistId": "default",
  "assignments": {}
}
```

**未显式分配的文件归属规则**：
- **tracked 文件**（modified/added/deleted/renamed/conflicted）→ 视为归属到 `activeChangelistId`
- **untracked 文件** → **不归属任何 changelist**，独立显示在 "Unversioned Files" 折叠群组下（详见 §7.3）。仅当用户显式 Move 后才进入 changelist。

这些隐式归属/不归属不立即持久化——只在用户首次显式 move / delete / create 等写操作时才落盘，避免空白仓库留下脏数据。

### 2.3 写语义

- 原子写：先写 `<file>.tmp`，再 `fs.rename` 覆盖（POSIX/Windows NTFS 均为原子）
- 解析失败处理：读取抛错时，记录到 Output Channel，弹一次性 toast「变更列表配置读取失败，本次不会保存更改」，不覆盖磁盘文件
- 自写保护：`ChangelistService.flush()` 调用前后 100ms 内设置 `recentWriteAt` 时间戳；`GitWatcher` 触发 changelists 重载时检查该戳，跳过自写引起的事件

## 三、设置项

在 `package.json` 的 `contributes.configuration` 中声明。文档 §7 共列了 6 个键，其中 `changelists.storageFile` 因持久化位置已固定为 `.vscode/jetgit-changelists.json`（用户决策）而**不暴露**。实际声明 5 个键：

| 设置键 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `changelists.allowMultiChangelistPerFile` | boolean | `false` | 是否启用行级 hunk 分配（关闭后右键菜单隐藏 "Assign Hunks…"） |
| `changelists.highlightInactiveFiles` | boolean | `true` | 非活动列表中的文件在 Commit 面板显示浅蓝色（与 IDEA 习惯一致） |
| `changelists.conflictBehavior` | enum | `prompt` | 编辑非活动列表文件时的行为：`prompt` / `move` / `switch` / `ignore` |
| `changelists.removeEmptyChangelists` | enum | `silent` | 列表变空后的处理：`doNothing` / `silent`（自动从活动列表移除）/ `confirm` |
| `changelists.showEmptyChangelists` | boolean | `true` | 是否显示空列表 |

## 四、后端服务层

### 4.1 `ChangelistService` 类

文件：`src/changelists/changelistService.ts`

构造：`new ChangelistService(gitRoot: string, notifier: GitStateSink)`。

读取/写入 JSON 文件路径由 `gitRoot` 推导（`path.join(gitRoot, '.vscode', 'jetgit-changelists.json')`）。监听 `vscode.workspace.onDidChangeConfiguration` 过滤 key 前缀 `changelists.` 热更新内存中的设置快照。

公共方法：

```ts
// 读
getChangelists(): Changelist[]
getActiveChangelistId(): string
getDefaultChangelistId(): string
/** 包括为未分配文件补全的 "默认归属到活动列表" 隐式记录 */
getEffectiveAssignments(): Record<string, FileAssignment>
getSettings(): ChangelistSettings

// 写（全部走 flush；校验失败抛 ChangelistError）
createChangelist(name: string, comment?: string): Changelist
renameChangelist(id: string, newName: string): void
deleteChangelist(id: string): void
setActiveChangelist(id: string): void
setChangelistComment(id: string, comment: string): void
moveFileToChangelist(filePath: string, targetId: string): void
removeFileFromChangelist(filePath: string): void
assignHunks(filePath: string, hunks: HunkAssignment[]): void
clearHunksForFile(filePath: string): void

// 持久化
reload(): Promise<void>      // 监听器或手动刷新时调用
flush(): Promise<void>       // 写盘原子操作
```

校验规则（抛 `ChangelistError`）：

- `renameChangelist`：`newName` 非空、不与其他列表重名（大小写不敏感）。默认列表 "Changes" 允许重命名（如改为 "我的默认"），但 `isDefault` 标记永远不变。
- `deleteChangelist`：默认列表拒绝。删除非默认列表时，扫描 `assignments`：该列表的整文件分配 → 改归默认列表；hunks 中属于该列表的项 → 丢弃；hunks 中其他列表对该文件的项保留。
- `setActiveChangelist`：目标列表必须存在。任何列表（含默认）均可设为活动；同时确保 `activeChangelistId` 全局唯一。
- `moveFileToChangelist`：目标列表存在；若文件已有 `hunks` 分配，整文件移动后清空 hunks（避免新旧归属不一致）。

### 4.2 观察 `.vscode/jetgit-changelists.json` 变化

新增分类条目到 `src/watchers/classify.ts`：

```ts
// .vscode/jetgit-changelists.json → worktree
if (relPath === '.vscode/jetgit-changelists.json') return GitDomain.Worktree;
```

工作区 → worker 的 source pattern 默认已包含 `.vscode/`（见 ARCHITECTURE.md §六 源 B），不需要修改 `GitWatcher` 本身。

`ChangelistService` 订阅 `worktreeChanged` 事件：当变化的路径等于 JSON 文件路径时调用 `reload()`；否则忽略（不重复 reload）。

### 4.3 Hunk 解析模块

文件：`src/git/gitService/hunks.ts`

导出：

```ts
async function getFileHunks(ctx: GitContext, filePath: string): Promise<HunkInfo[]>
```

实现：调 `git diff --no-color HEAD -- <filePath>`，按 `diff --git` / `--- a/` / `+++ b/` / `@@ -a,b +c,d @@` 切块，返回每个 hunk 的 `{ startLine, endLine, oldStart, oldCount, contextBefore, contextAfter, patchText }`。

依赖 `parsers.ts` 中的现有 unified-diff 解析辅助函数（已有）。

### 5.3 `commitChangelist` 实现细节

**Commit message 预填**（IDEA 行为）：webview 端点击 "Commit This Changelist" 时，若该 changelist 的 `comment` 非空，弹一个带预填内容的 QuickPick/InputBox；用户可在提交前修改 message。`commitChangelist` 命令的 `message` 参数始终是用户最终确认的内容（已包含可能的修改），`comment` 仅作为初始值。预填**总是启用**，无设置项控制。

```ts
async function commitChangelist(changelistId, message, amend) {
  const targets = await buildCommitTargets(changelistId);
  // targets = { files: [{ path, mode: 'whole' | 'hunks', hunks?: HunkAssignment[] }] }

  try {
    // 1. 清空 index（不碰工作区）
    await execGit(['reset', 'HEAD', '--', '.']);

    // 2. 按目标 staging
    for (const file of targets.files) {
      if (file.mode === 'whole') {
        await execGit(['add', '--', file.path]);
      } else {
        const fullPatch = await execGit(['diff', 'HEAD', '--', file.path]);
        const filtered = filterPatchByHunks(fullPatch, file.hunks);
        if (filtered.trim()) {
          const tmp = path.join(os.tmpdir(), `changelist-${uuid()}.patch`);
          await fs.writeFile(tmp, filtered);
          try {
            await execGit(['apply', '--cached', tmp]);
          } finally {
            await fs.unlink(tmp).catch(() => {});
          }
        }
      }
    }

    // 3. 提交，仅指向这些文件
    await execGit(['commit', '-m', message, '--', ...targets.paths]);

    // 4. 清空 index，确保其他列表的「未暂存」状态保持纯粹
    await execGit(['reset', 'HEAD', '--', '.']);

    notifier.notify(Worktree, Refs);
    messageRouter.broadcastEvent('changelistsChanged', undefined);
    return { success: true, committedFiles: targets.paths };
  } catch (err) {
    // 失败回滚：撤销 staging
    await execGit(['reset', 'HEAD', '--', '.']).catch(() => {});
    throw err;
  }
}
```

`buildCommitTargets` 根据 `getEffectiveAssignments()` 计算：整文件分配 + hunk 分配（即使同一文件在其他列表还有别的 hunk，本列表只关心自己的 hunk 集合）。

`filterPatchByHunks` 算法：对 `git diff` 输出，保留 `diff --git` / `--- a/` / `+++ b/` 文件头；但只保留 `@@ ... @@` 头与 +/- /空格行**全部落在**目标行号区间内的 hunk。空文件 patch 丢弃。

### 5.4 `shelveChangelist` 实现

与 `commitChangelist` 共享 `buildCommitTargets`：算出该 changelist 涉及的所有文件 + hunk 子集。

1. hunk 分配的文件：先 `git diff HEAD -- <file>` 取 patch，过滤出本列表的 hunk 子集，写临时 patch 文件，`git apply --cached <patch>` 暂存 → `git stash push -m "<shelf-name>" -- <file>`（stash 整个文件版本，含被暂存的部分）
2. 整文件分配：`git stash push -m "<shelf-name>" -- <file>`
3. 默认 shelf 名：`<changelist-name>_<timestamp>`（避免与现有 stash 冲突）；用户传 `message` 时用 `message` 作 stash message
4. 完成后 `notifier.notify(Stash, Worktree)` 与 `changelistsChanged`
5. shelve 后该 changelist 的 assignments 不清除（IDEA 行为：从 shelf unshelve 后归属可恢复）——但暂存区被清空；用户在 webview 看到列表仍存在但工作区是 clean 状态。

### 5.5 `createPatchFromChangelist` 实现

1. 计算目标文件列表（与 shelve 同源）
2. hunk 分配的文件：合成 patch = `git diff HEAD -- <file>` 过滤出本列表的 hunks
3. 整文件分配的文件：直接 `git diff HEAD -- <file>` 取整文件 patch
4. 把所有 patch 拼到 `os.tmpdir()/jetgit-<uuid>.patch`
5. 调 `vscode.window.showSaveDialog` 让用户选保存路径，默认 `<workspaceRoot>/<changelist-name>.patch`
6. 复制 tmp 文件到目标路径，返回 `{ patchPath }`
7. 不动 git 状态（纯只读操作）

## 六、编辑冲突检测

### 6.1 监听器

在 `extension.ts` `activate()` 中新增：

```ts
context.subscriptions.push(
  vscode.workspace.onDidChangeTextDocument(async (event) => {
    if (!event.document.uri.scheme.startsWith('file')) return;
    const filePath = vscode.workspace.asRelativePath(event.document.uri, false);
    if (!filePath || filePath.startsWith('..')) return;

    const assignment = changelistService.getAssignment(filePath);
    if (!assignment) return;
    const activeId = changelistService.getActiveChangelistId();

    // 整文件分配 + 非活动列表
    if (!assignment.hunks?.length && assignment.changelistId !== activeId) {
      await handleInactiveFileEdit(filePath, assignment.changelistId);
      return;
    }

    // hunk 分配 + 改动发生在非活动 hunk 行范围内
    if (assignment.hunks?.length) {
      const changedRange = computeChangedRange(event);
      const offending = assignment.hunks.filter(
        (h) => h.changelistId !== activeId
            && rangesOverlap(changedRange, [h.startLine, h.endLine]),
      );
      if (offending.length) await handleInactiveHunkEdit(filePath, offending);
    }
  }),
);
```

### 6.2 行为分派

`changelists.conflictBehavior` 设置：

- `prompt`（默认）：弹模态 QuickPick「移入活动列表 / 切换活动列表到该文件 / 忽略」，执行用户选择
- `move`：静默 `changelistService.moveFileToChangelist(filePath, activeId)`
- `switch`：静默 `changelistService.setActiveChangelist(filePath 的所属列表)`
- `ignore`：什么都不做

### 6.3 Hunk 级编辑冲突

仅把**那个 hunk** 重新归属到活动列表，整文件与其它 hunk 不变。新分配覆盖旧的同范围 hunk 分配。

### 6.4 与内置 Git SCM 协同

VS Code 内置 Git 也监听同一事件，但只影响 `Untracked` 分类，与本插件归属无关。无协同需要。

### 7.6 Hunk 分配对话框

1. 用户右键文件行 → 「Assign Hunks…」
2. webview 调 `getFileHunks` → 拉当前文件的所有 hunk 信息
3. 对话框渲染：每个 hunk 一行，左侧 diff 预览（前 5 行 + 后 5 行上下文 + +/- 行高亮），右侧下拉「Active / Changes / [其它列表]」
4. 用户调整 → 「Confirm」 调 `assignHunks` 一次性提交
5. 关闭对话框，列表自动刷新

固定行号策略的失配：

- webview 渲染 hunk 分配时，调 `getFileHunks` 重新拉（节流 5 秒缓存）
- 若某存储的 `[startLine, endLine]` 不再与任何当前 hunk 重叠 → 该 hunk 视为失效，从 changelist 移除，整文件自动回退归属默认列表
- 顶部一次性 toast：「N 个 hunk 因文件改动已失效，已回退到 Changes」

### 7.7 高亮非活动文件

`changelists.highlightInactiveFiles = true` 时，非活动列表的文件在 Commit panel 中显示浅蓝色字（CSS class `changelist-inactive-file`，颜色 `var(--vscode-charts-blue)`）。

### 7.8 拖拽支持

文件行支持 HTML5 拖拽到目标 changelist 组。实现细节：

- `ChangelistGroup.tsx` 顶层 `<div>` 上加 `onDragOver={(e) => { e.preventDefault(); setHover(true); }}` 与 `onDragLeave={() => setHover(false)}`；drop 时 `onDrop={(e) => { e.preventDefault(); handleDrop(e.dataTransfer.getData('application/x-jetgit-file-paths')); }}`
- `FileItem.tsx`（已存在）的 `draggable={true}` + `onDragStart={(e) => { e.dataTransfer.setData('application/x-jetgit-file-paths', JSON.stringify([filePath])); e.dataTransfer.effectAllowed = 'move'; }}`
- 拖拽多个文件：先用 `setFileKeys` 选中，再拖拽其中一个——drop handler 从 `highlightedFiles` + 拖拽源文件取并集
- 视觉反馈：drop 目标高亮蓝色边框 + 半透明蓝色背景
- drop 后调 `moveFileToChangelist` 完成移动；不需要再走右键菜单

注：HTML5 drag-and-drop 在 webview 内是原生的，不需要 VS Code `TreeDragAndDropController`。但 webview `<iframe>` 边界可能截获某些事件——实测再调整；如果原生 DnD 不可靠，回退到右键菜单（已经覆盖所有用例）。

## 十、风险与权衡

1. **Hunk 行号漂移**：固定行号策略在文件中间插入行后，后续行号全部偏移。文档 §5.2 的 hash + context 匹配被简化掉。代价：用户改完文件后部分 hunk 失效，会一次性看到多条 toast。**回退路径**：未来可加 hash 匹配，扩展 `HunkAssignment` 加 `contentHash` 字段，向 v3 迁移。

2. **提交期间 index 暂态**：`git reset HEAD -- .` → `git apply --cached` → `git commit -- <paths>` → `git reset HEAD -- .` 四步流程在外部异常（断电、kill）下可能留下半 staged 状态。**缓解**：失败 catch 块里执行 reset；正常完成也会 reset。极端情况靠用户手动 `git reset` 兜底。

3. **Commit panel 与内置 Git SCM 共存**：VS Code 内置 Git 也显示 working tree changes，用户可能在两个 UI 间切换。本插件的归属对内置 Git **不可见**——这是文档要求的行为（归属是个本地概念），但要避免误导用户。**缓解**：Changelists tab 顶部加一行说明文字（设置项"IDEA Git: Changelists 归属仅在 JetGit Commit 面板内生效"）。

4. **多工作区**：当前 `ChangelistService` 按 `gitRoot` 实例化一个，每个 git 仓库独立。跨仓库的 changelist 隔离是默认行为，符合直觉。

5. **`.vscode/` 在 .gitignore**：本插件**不自动修改** `.gitignore`。若用户不想把 `jetgit-changelists.json` 提交到 git，需要自己添加忽略行。这是与文档 §8 把文件放在 `.git/` 的差异——换来 vscode 习惯一致性。

## 十一、不在本设计范围

- 跨仓库共享变更列表
- 与 IDEA `.idea/shelf/` 双向同步
- 基于内容的 hunk 智能匹配（hash + context）
- VS Code 原生 SCM provider 渲染（用户已选择 webview 内集成）
- 拖拽到文件外部创建变更列表（UI 复杂度高；右键 + 菜单覆盖）
- 远程分支级别的 changelist 视图
